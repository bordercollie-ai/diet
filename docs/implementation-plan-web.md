# Web/PWA implementation plan

Read `docs/prd.md` and ADR 0002 first. Implement phases in order; domain calculations, validation, backup, and merge logic remain independent of Svelte and browser adapters.

## Global rules

- Svelte + TypeScript + Vite; use `pnpm` in `web/`.
- IndexedDB only: no account, server, cloud sync, or runtime network dependency.
- Deterministic tests cover domain behavior; browser checks cover offline/PWA/accessibility flows.
- Invalid input and failed imports must be visible and must not produce partial writes.
- Keep dependencies limited to the existing Svelte/Vite toolchain.

## Store boundary

```text
load() -> AppData
save(AppData) -> Result
export() -> BackupFile
import(BackupFile) -> ImportPreview | ImportError
```

## Out-of-band feature: custom food QR/text sharing and camera/paste import

**Status:** done (2026-08-30).

- **Scope:** a custom (`source: 'user'`) food's edit sheet gained a "Share food" button opening a dialog with a QR code and an equivalent compact text code (identical payload — name, description, serving, nutrition, detail; never id/source/updatedAt), plus Copy image, Copy text, and native Web Share (`navigator.share`, with a file-share attempt first, falling back to sharing the text code) actions. The Foods tab gained an "Import food" button opening a dialog with a "Paste a shared food code" field (always available) and, where the browser supports the native `BarcodeDetector` Shape Detection API, a camera-scan option; unsupported browsers (e.g. iOS Safari without the experimental flag) show guidance to use the paste field instead. A decoded code always creates a brand-new local custom food — it can never overwrite or collide with an existing one. Bundled foods and quick/logged meal entries are explicitly out of scope, per instruction. No network request or product-database lookup is involved at any point (see `docs/prd.md` clarification distinguishing this from the excluded retail-barcode-scanning feature).
- **Design:** `encodeFoodShareCode`/`decodeFoodShareCode` (in `web/src/domain/store.ts`, pure/Svelte-independent) produce/parse a `DIETFOOD1:`-prefixed base64url-encoded JSON payload — UTF-8 safe (via `TextEncoder`/`TextDecoder`, not the deprecated `escape`/`unescape`), reusing `validNutrition`/`invalid` for the same validation `validateFood` already applies. QR generation uses the actively-maintained `qrcode` npm package (rendered to a `<canvas>`); QR *scanning* deliberately uses the browser-native `BarcodeDetector` API instead of adding a scanning library (the obvious option, `jsqr`, hasn't been updated in 5 years) — no new runtime dependency, and it degrades gracefully to the always-available text-paste path.
- **Files changed:** `web/src/domain/store.ts` (codec), `web/src/pages/FoodSheet.svelte` (Share button/dialog), `web/src/pages/FoodsPanel.svelte` (Import button/dialog, camera scan loop), `web/src/App.svelte` (wires `onImportFood`), `web/src/lib/i18n.svelte.ts` (en/zh/ja strings), `web/tests/store.test.ts`, `web/tests/FoodSheet.test.ts` (new), `web/tests/FoodsPanel.test.ts`, `web/package.json`/`pnpm-lock.yaml` (added `qrcode` + `@types/qrcode`), `docs/prd.md`.
- **Checks:** `pnpm check` (0 errors/warnings); `pnpm build` (pass; pre-existing chunk-size warning); `pnpm test` (44 domain tests, includes share-code round-trip, non-ASCII names, and malformed-code rejection); `pnpm run test:ui` (42 UI tests) — all pass.
- **Risk / limitations:** camera QR scanning depends on `BarcodeDetector` browser support (broad on Chromium/Android; on iOS Safari it requires manually enabling Settings > Safari > Advanced > Feature Flags > Shape Detection API, and per public reports is currently broken on iOS 18 even when enabled) — the text-paste path has no such dependency and was kept as a first-class, always-available option specifically to cover this gap and to make cross-family sharing/verification easy without a working camera. No test exercises the live camera or `BarcodeDetector` path (jsdom doesn't implement either); coverage there is the manual browser-support fallback rendering only.
- **Skipped:** sharing bundled foods and quick/logged meal entries (explicitly out of scope per instruction); a dedicated QR-scanning fallback library for browsers without `BarcodeDetector` — add only if native support proves insufficient in practice.
- **2026-08-30 bug fixes (dialog sizing, secure context, and in-app camera scanning):**
  - Fixed both dialogs (`FoodSheet.svelte` share, `FoodsPanel.svelte` import) overflowing/clipping off-screen on shorter iPhone viewports: the shared `Dialog.Content` base class centers via `top-1/2 -translate-y-1/2`, and overriding only `top-[X%]` doesn't cancel the transform. Both now use `top-[6%] max-h-[88vh] translate-y-0 ... overflow-y-auto`.
  - `getUserMedia`/`BarcodeDetector` require a secure context; plain-HTTP LAN dev access silently blocks the camera with no prompt. Added `@vitejs/plugin-basic-ssl` (dev-only, `apply: 'serve'`) + `server: { host: true }` to `vite.config.js` so on-device testing works over `https://<lan-ip>:5173`.
  - Fixed a real bug in `FoodsPanel.svelte`'s `startScan()`: it bound `videoEl.srcObject` before setting `scanning = true`, but `<video>` only mounts inside `{#if scanning}` — so `videoEl` was still `undefined` and the stream was silently dropped. Fixed by flipping `scanning` first, then `await tick()` before touching `videoEl`.
  - Added an on-screen debug readout (frame count, video resolution, detection count) in the import dialog since the phone under test had no attached remote devtools — this was essential to diagnosing the remaining issues below.
- **2026-08-30 finding — iOS Safari's `BarcodeDetector` does not reliably detect real QR codes:** after the above fixes, the camera preview worked and captured frames at full resolution (confirmed up to 1080x1920), and the QR code itself was independently confirmed valid and decodable (a third-party barcode app and an online decoder both read it correctly), yet `BarcodeDetector.detect()` — tried against both a canvas snapshot of the video frame and the live `<video>` element directly, per MDN's standard usage — consistently returned zero results after 1000+ frames. This matches public reports that WebKit's Shape Detection API implementation is unreliable/non-functional for barcode detection in practice even when the experimental flag is enabled (whatpwacando.today itself disclaims "does not work on iOS 18"; this was observed on iOS 26.6.1, so the gap persists on much newer versions too). Two contributing/adjacent issues were also fixed regardless since they're correct regardless of the above: QR generation used `margin: 1`, below the QR spec's 4-module minimum quiet zone (now uses the library default); and `getUserMedia` didn't request a resolution (browser default was as low as 480x640, too coarse for a dense QR), now requests `{ width: { ideal: 1920 }, height: { ideal: 1080 } }`.
  - **Fix — URL deep-link, bypassing the unreliable in-page scanner entirely:** the share code is now wrapped as a URL (`foodShareUrl()` in `store.ts`, `<origin+path>#import=<encoded code>`) and it's this URL — not the raw code — that's rendered as the QR, shown in the copyable text field, and passed to `navigator.share`. `decodeFoodShareCode()` transparently accepts either form (raw code, full URL, or just the `#import=...` hash) by stripping the hash prefix before decoding, so the paste-import path is unaffected. `App.svelte`'s `onMount` checks `location.hash` for `#import=` on load and auto-imports, switching to the Foods tab. This means the **system Camera app** (which reliably reads QR codes on iOS, unlike the in-page `BarcodeDetector`) can now scan the QR and deep-link straight into a working import, without touching our own camera-scan code path at all. The in-page `BarcodeDetector` scanner is left in place as-is for browsers where it does work (e.g. Chromium/Android), with the text-paste path remaining the universal fallback.
  - **Files changed:** `web/src/domain/store.ts` (`foodShareUrl`, hash-stripping in `decodeFoodShareCode`), `web/src/pages/FoodSheet.svelte` (QR/text/share now use the URL), `web/src/App.svelte` (hash-based auto-import on load), `web/src/pages/FoodsPanel.svelte` (resolution constraint, debug readout), `web/tests/{store,FoodSheet}.test.ts`.
  - **Checks:** `pnpm check` (0 errors/warnings), `pnpm build` (pass), `pnpm test` (45 domain tests), `pnpm run test:ui` (42 UI tests) — all pass.

The in-page `BarcodeDetector` path remains unverified end-to-end on any real device (only the new URL deep-link path has a plausible fix); if it turns out to never work on iOS Safari in practice, consider hiding the "scan with camera" option behind stronger feature detection (e.g. a successful trial detection) rather than just `'BarcodeDetector' in window`, to avoid presenting a non-functional affordance.
- **2026-08-30 bug fix — hash cleared before being read:** `App.svelte`'s `onMount` called `history.replaceState(...)` (which clears `location.hash`) *before* passing `location.hash` to `decodeFoodShareCode`, so the deep-link import always failed with "Invalid data: share code" — decoding an already-emptied string. Fixed by capturing `location.hash` into a local variable first. Added a regression test in `App.test.ts` that sets `location.hash` to a real `foodShareUrl()` output before rendering `App` and asserts the food is auto-imported, the Foods tab is shown, and the hash is cleared (so a refresh can't re-import a duplicate). **Also clarified (not a code bug):** during multi-device dev testing, the QR/URL bakes in whatever `location.origin` the *generating* device's tab was on — sharing from a desktop tab at `http://localhost:5173` produces a URL that's meaningless to any other device, since "localhost" always means "this device". Cross-device dev testing requires generating the share URL from a tab already on the shared reachable LAN address (e.g. `https://<lan-ip>:<port>/diet/`); in production there's one canonical public domain, so this doesn't apply post-deploy. **Checks:** `pnpm check` (0 errors/warnings), `pnpm build` (pass), `pnpm test` (45 domain tests), `pnpm run test:ui` (43 UI tests, incl. the new regression test) — all pass.
- **2026-08-30 limitation — deep-link import lands in a different "container" than the installed PWA, depending on how it was opened:** the URL deep-link fix (above) is only as good as where tapping it actually opens. On iOS, a plain web PWA cannot register itself as the handler for a tapped `https://` link (that requires Universal Links / Associated Domains, only available to a native app wrapper — out of scope here), so a scanned link always opens in some browser context, never directly into the installed standalone app window. Two cases were distinguished: (1) opened via the **stock Camera app** (or typed directly), it opens real Safari, which shares its on-device storage (IndexedDB included) with the installed PWA of the same origin — the imported food reliably shows up when the user later opens the installed app icon, no data loss. This second case is a limitation of that specific third-party app's WebView configuration, not something fixable from this project's pure-web-PWA architecture. **Recommendation (documented for users/testers):** use the stock Camera app to scan, or use the always-reliable paste-import flow performed directly inside the real installed app (which is immune to this issue, since it never depends on what opened a link). **Skipped:** no in-app UI change was made for this (e.g. a "please reopen the app" banner) — revisit only if user reports indicate it's a recurring point of confusion in practice.

### Rules and design

- The shared `calorieTone()` qualifies a nonzero calorie day at or below its target (≤100%). Reuse it for achievement qualification so the calendar, summary green circle, and achievements have one definition of on-target. A missing, over-target, or unavailable-target day breaks a qualifying run.
- The first release has exactly 22 achievements, calculated only from existing `AppData`:

  | Family | Thresholds | Titles |
  | --- | --- | --- |
  | Valid saved profile and targets | 1 | Ready Set |
  | Recorded meals | 1, 10, 50, 100 | First Plate, Tenfold Log, Fifty Plates, Hundred Plates |
  | Temporary calorie entries | 5 | Quick Start |
  | Days with at least one meal | 3, 7, 30, 100 | Three-Day Start, Week Witness, Monthly Companion, Hundred-Day Journal |
  | Consecutive on-target days | 3, 7, 14, 30 | Steady Starter, Seven-Day Rhythm, Two-Week Pace, Monthly Rhythm |
  | Entries of one identified food | 10, 25, 50 | Familiar Favorite, Regular, Signature Order |
  | Unique identified foods / custom foods | 10, 25, 50 / 1, 5 | Ten Tastes, Twenty-Five Tastes, Fifty Tastes / First Custom Food, Personal Pantry |

- A temporary calorie entry has no `foodId`, so it counts toward recorded meals, its five-entry onboarding achievement, and active days but never food-specific, unique-food, or custom-food achievements. Titles remain unlocked after a later break or food deletion.
- Persist achievement records in `AppData` (optional for backward-compatible backups): ID, first `unlockedAt`, and optional `readAt`. Do not store duplicate daily summaries or a second source of nutrition truth.
- A small trophy button sits at the header's right edge and shows a non-intrusive unread indicator only while an achievement lacks `readAt`. Its page opens directly to a badge list; selecting a badge pushes a real detail sheet above that still-mounted list, revealing the exact list on swipe-back.
- On each save, unlock every newly qualified achievement in definition order and give that batch one shared `unlockedAt`. Never queue or stack toast/dialog celebrations.
- The badge list places all unread records in a "New" group above the normal list. Mark them all read when the list opens. Only those unread cards receive a short CSS-only entrance: the card scale/fades in while its badge flips once around the Y axis; read cards never animate or trigger a popup again. Honor `prefers-reduced-motion`. No image assets, canvas, or animation library.
- Use existing Lucide crown/star icons, CSS shapes, and the relevant threshold numeral for simple self-contained badge art.
- Evaluate achievements whenever local data is saved. A profile/target change can affect future qualification checks but never removes a previously unlocked title.
- A valid saved profile is one accepted by `validateProfile()` whose targets resolve successfully; unlock Ready Set on its first successful profile save, not on the prefilled unsaved form.
